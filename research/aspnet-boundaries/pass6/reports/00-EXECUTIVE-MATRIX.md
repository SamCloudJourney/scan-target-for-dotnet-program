# Sixth-pass validation — 16 November 2026

Scope: controlled ASP.NET Core 10.0.15 (.NET SDK 10.0.404) and ASP.NET Core 11.0.0 (.NET SDK 11.0.100), GitHub-hosted Ubuntu runners, services bound to 127.0.0.1 / 127.0.0.2. No third-party exploitation, production credentials, personal data, or real protected resources. Written evidence, exact version logs, request/response records and executed code are retained in GitHub Actions artifacts and in the compiled ZIP delivered with this report.

**MSRC classification is provisional investigator judgment, not Microsoft assessment.** These candidates have existing public engineering changes; a reproduced parser/caching discrepancy and a valid MSRC bounty are not equivalent.

## Reproducibility and statistical reading
- Eight-listener path corpus used 32 **fixed, documented** paths in origin and absolute form. Proxy-only policy misses: HAProxy raw 32/28 (net10/net11), Nginx raw 28/28, HAProxy normalized case-sensitive 2/2, Nginx normalized case-sensitive 2/2, YARP 0/0, HAProxy normalized case-insensitive 0/0, Nginx normalized case-insensitive 0/0. **Do not interpret misses as individual CVEs.**
- A proxy-only protected write to the synthetic backend counter succeeded **3 times on net10 and twice on net11** through the intentionally weak HAProxy raw ACL (origin-form and absolute-form tested; write suite uses absolute-form). The separately protected app-auth write counter stayed **0** on both.
- The HTTP/2 encoded-slash path did not match the protected route in either version (404); normalized dot segments were routed in both, while proper app authorization remained 401.
- Public OutputCache concurrent requests: **18 GETs, one fixture execution, one response body** on each runtime.
- Redis two-process test used a deliberately shared logical HTTP Host and a genuine local Redis store. Worker B served the response generated by worker A for a distinct decoded query; distinct key and explicit invalidation controls worked.

## Corrections / rejected interpretations
An early corpus test erroneously substituted path text only when it contained the literal `/gate/read`. Encoded-separator probes therefore accidentally targeted the **public** route and were mislabelled as application auth bypasses. The corpus was corrected to rewrite the terminal endpoint name and assert transformation, then re-run. **Final result: zero application authorization bypasses.**

Other initial failed CI attempts were test setup errors: a malformed HAProxy config (fixed), a HEAD request that mapped to 404 in the fixture (expectation corrected), and mismatched Host values plus a variable shadowing error in the Redis harness (corrected with independent same-key sharing control). Failures have not been silently treated as vulnerabilities.

## Next genuinely useful gate
A new MSRC Important case requires an otherwise secure supported default customer configuration crossing a Microsoft-owned boundary. More path spelling variants against an intentionally weak proxy ACL do not establish that condition; all additional testing should prioritize issue novelty, actual security impact and separately enforceable auth policy.

## Seventh pass — actual Chromium CORS request replay

[Final two-version run](https://github.com/SamCloudJourney/scan-target-for-dotnet-program/actions/runs/43915322085) passed **10/10 browser checks for each runtime**, plus 10/10 HTTP cache seed checks per runtime. An actual Chromium 157 document at `http://127.0.0.1:5207` fetched a different-origin cached ASP.NET response at `http://127.0.0.1:5200`. The public A response carried `Access-Control-Allow-Origin: http://127.0.0.1:5207`. Its colliding public B URL returned that cached A representation and a browser-origin JavaScript fetch succeeded. The noncolliding B control (`Access-Control-Allow-Origin: null`) failed with a browser `TypeError`. Credentialed requests failed and all responses contained artificial, public lab content.

ResponseCaching had the same cross-origin public-content substitution on **.NET 10 with a normal browser fetch**, but not on .NET 11. A `cache: "no-store"` browser fetch bypassed this ResponseCaching replay on both tested runtimes. This is a **browser-visible replay of A under B's URL, not unauthorized reading of B's original protected data**. No private data leak, browser XSS, or credential disclosure was demonstrated.

The original all-five disposition is unchanged: #5/#6 public response integrity defects already known to upstream, #8 proxy-only policy mismatch, #7 unsafe rewrite, #4 request-derived Domain injection unproven.
